================================================================================
HOW THE REAL AUTHENTICATIONS WERE PRODUCED
================================================================================

The spec asks for real SSH logins rather than synthetic events. These were not
staged: the verifier's own pull path produces them. Every verification run
authenticates to the `verify` account on the primary over SSH, so driving
verification drives genuine authentications, and the emitter's --tail mode on
/var/log/auth.log captures them as they occur.

The false-positive check therefore exercises the production mechanism rather than
a simulation of it.

--- The captured set is NOT "SSH logins", and must not be described as such ---

emitter.py's AUTH_MARKERS list includes the PAM strings "session opened for user"
and "session closed for user". Those are not sshd-specific: they match sudo, cron
and systemd-user sessions too. The comment in the source claimed the filter was
deliberately narrow. It was not, and the comment has been corrected.

The breadth is worth keeping. An audit trail recording only SSH would miss
privilege escalation through sudo and anything scheduled through cron, which are
precisely the events an investigation cares about. But the write-up must describe
this as authentication and session events, of which SSH is a subset.

Relevant to any future event-rate estimate: a five-minute verification timer
produces roughly one forwarded event per minute from pulls alone.
