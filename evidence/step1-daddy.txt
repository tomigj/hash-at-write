READING THIS CAPTURE
================================================================================

Exactly one inbound rule: TCP 9900 from the primary only. This is the write-only
digest path. Nothing else inbound is permitted, by default policy, over either
address family -- `Default: deny (incoming)` covers IPv6 as it does on the
primary.

`disabled (routed)` confirms no forwarding. This host does not bridge the zones.

**The SSH listener is present and must be described accurately.** `ss` shows sshd
bound to 0.0.0.0:22 and [::]:22. openssh-server is installed here and
socket-activated, exactly as on the primary. So the statement "the primary has no
inbound SSH path to the ledger" is true by FIREWALL POLICY, not by the absence of
a daemon. The distinction matters: an attacker who could alter this host's
firewall would find a listener waiting, whereas one who could alter a host with
no SSH server installed would not.

Nothing in the threat model depends on the difference -- the threat model assumes
the ledger is not compromised -- but the write-up must not claim the ledger runs
no SSH server, because it does.

This was very nearly recorded wrongly. The original step 1 instruction used
`systemctl is-active ssh` as the test for "sshd is off here", and that command
reports `inactive` on both hosts while port 22 is listening, because Ubuntu 24.04
ships SSH socket-activated. Filed under that check, this capture would have
asserted the ledger had no SSH listener while it had one on every interface.
`ss -tlnp` is the check that answers the question.
