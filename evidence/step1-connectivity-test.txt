Connectivity test — does the rule on `tg` do what the write-up claims?

Run from the ledger host `daddy` (10.0.0.212) against the primary `tg`
(10.0.0.173). Probes are TCP connect attempts; no login was performed and no
credentials were used.

Rule under test, from tg's `ufw status verbose`:

    22/tcp    ALLOW IN    10.0.0.212    # verifier pull from ledger
    Default: deny (incoming), allow (outgoing), disabled (routed)

================================================================================
2026-09-10 03:45:18 UTC — probes begin
================================================================================

POSITIVE  10.0.0.212 -> 10.0.0.173:22     OPEN
          The allow rule matches: correct source, correct port.

NEGATIVE  10.0.0.212 -> 10.0.0.173:9900   blocked (hung, timed out at 8s)
          Same source host, same firewall, no rule for this port.

NEGATIVE  10.0.0.212 -> 10.0.0.173:80     blocked (hung, timed out at 8s)
          As above.

2026-09-10 03:45:34 UTC — probes end

================================================================================
WHAT THIS DEMONSTRATES, AND WHAT IT DOES NOT
================================================================================

Demonstrates: the allow rule is scoped to a single port and everything else
inbound is denied by default policy. The only variable between the positive and
negative results is the destination port -- same source address, same host, same
firewall, same moment. The probes hung rather than being refused, which is
consistent with DROP rather than REJECT.

Does NOT demonstrate: that a DIFFERENT SOURCE ADDRESS is blocked on port 22.
That is the other half of the rule and it is not tested here. The lab has two
machines and the allow rule names one of them, so no third source address is
available on the LAN.

An IPv6 negative test was designed for this purpose -- tg's allow rule is
IPv4-only while sshd listens on [::]:22, so a v6 connection from the same host
would isolate the rule's address-family scope. It could not be run: `daddy` has
no IPv6 address and no default v6 route on its LAN interface, because the VPN
client in use disables IPv6 to prevent leaks. The attempt fails instantly with
"Cannot assign requested address", which is the local stack refusing to source
the packet -- not the remote firewall dropping it. Recorded here rather than run,
because a test that fails for the wrong reason is worse than no test.

Outstanding to complete the matrix: a third LAN host attempting port 22, or the
IPv6 test run with the VPN disconnected. Either would close the source-address
half of the rule.
