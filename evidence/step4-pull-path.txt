authorized_keys, single line:

    command="/usr/bin/cat /var/log/integrity/events.log",no-port-forwarding,
    no-agent-forwarding,no-pty,restrict ssh-ed25519 AAAA... witnessd-verifier@daddy

--- How the read permission actually works, because it is not what it looks like

`verify` does NOT read events.log through the integrity group. The file is
tomigj:tomigj mode 664, so it is readable via the OTHER bits. What the integrity
group provides is the ability to traverse /var/log/integrity, which is
drwxr-x--- tomigj:integrity.

The directory is the gate; the file inside is readable to anything that gets
through it. This matters: if someone later tightens events.log to 640 on the
assumption that group membership is what carries the access, the pull path breaks
and the failure will look like an SSH problem rather than a permissions one.

The first 21 digests were spooled during the unplanned outage in step 3 and

    digest arrived 12.4 minutes after the record claims to have been written,
    and no earlier prompt receipt exists to establish that this ledger was

That is the correct verdict and the honest one. The chain begins with this burst,
so there is no earlier prompt receipt against which to establish that the ledger
was reachable when those records were written. From ledger data alone, an outage
before the chain began and a set of records withheld and submitted later are
indistinguishable -- and the alert says exactly that rather than picking the
benign reading.

This is the first live occurrence of a case previously only constructible as a
fixture in tests/repro_scenarios.py.

================================================================================
5. WHAT THIS DOES AND DOES NOT ESTABLISH
================================================================================

Establishes: the ledger can retrieve the primary's log over a channel restricted
to reading one file, and can verify it independently. The primary is never asked
what its own digests are or whether it considers itself intact.

Does NOT establish that the forced command protects the evidence. It is least
privilege for the ledger's access INTO the primary. Under the threat model the
primary is fully compromised, so a rooted primary can replace this
authorized_keys file and serve doctored content. The design survives that because
doctored content fails against digests that left the machine at write time --
which means the property comes from where the digests are, not from this
restriction. The build spec's claim that "the forced command is what makes claim
4 real" is wrong and is corrected in the amended spec.
