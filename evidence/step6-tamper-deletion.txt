Targets were chosen by CONTENT and named before any test ran, not by index. The

The value predicted independently on the primary and the value computed by the

--- The silence threshold demonstrated itself rather than being asserted -------

The agent must be stopped to edit the log cleanly, so the stop is itself part of
the attack. Verification was run before and after the threshold was crossed:

    at 150s elapsed:  TAMPER only, no SILENCE
    at 209s elapsed:  TAMPER + SILENCE seq=58->now, 3.5 minutes

Run at 150s, seen to be silent, waited 45 seconds, run again. The artefact shows
the boundary being crossed rather than a single reading taken afterwards.

That pairing is the exhibit: the attacker altered one field of one record, and
the system caught both the alteration AND the fact that the agent had to be
stopped to make it.

T3 — DELETION, WHICH TURNED OUT TO BE THE HARDER CASE
================================================================================

Restored to pristine first and confirmed byte-identical, so the deletion starts
from a clean log rather than a tampered one. Then the root login record was
removed entirely.

The result was subtler than planned. Seq 58 was the LAST record, so removing it
left the log contiguous:

    records: 57
    digest mismatches: 0        every remaining record hashes correctly
    seq range: 1-57
    missing sequences: []       NO GAP

There is no hole to notice. The log does not look like a log with a record
missing -- it looks like a log that ends at 57. Nothing on the primary
distinguishes "the root login was deleted" from "the agent stopped before it
happened". An auditor with root on that machine, examining the file with every
tool available to them, finds a perfect log.

Verification from the ledger:

What the ledger holds for a record that no longer exists anywhere on the primary:

Received three minutes before the record ceased to exist.

--- The alert hedges, and the hedge is correct --------------------------------

Beyond the log's highest sequence, the ledger genuinely cannot distinguish a
truncated tail from a digest submitted for a record that never existed. We know
it was truncation because we did it. The ledger does not, and the alert says so
rather than asserting the stronger claim.

A mid-log excision produces an unambiguous DELETION with a real gap and no hedge.
That test was run as T3b -- see below -- so both cases sit side by side.

--- The pair, and why the wordings differ -------------------------------------

    T3   removed the LAST record    log appears complete, ends at 57, no gap.
                                    Nothing on the primary indicates loss.
                                    DELETION 58, hedged: truncation or a digest
                                    for a record that never existed.

    T3b  removed a MIDDLE record    log has a visible hole at 57.
                                    DELETION 57, unhedged.

T3 is the harder case and the stronger statement of the thesis: an auditor with
root, examining that file with every tool available, finds nothing wrong. T3b
produces the cleaner alert.

Both belong in the exhibit. The hedge in T3 is not weakness — it is the ledger
declining to assert more than it can know — and T3b is the same mechanism
speaking plainly when it can. Presenting only T3b would hide the limit;
presenting only T3 would invite a reviewer to read the hedge as doubt.

--- A methodological correction to the documented command ---------------------

The command originally specified was `grep -v ... > /tmp/d.log` followed by `mv`.
`mv` replaces the destination inode and carries the source file's mode with it,
so the test can silently alter the permissions of the file it is testing -- and
the verify account reads that file through its mode bits. A test that changes the
access it depends on is a trap for whoever reproduces it.

T3b instead redirected to a scratch file and used `cat scratch > events.log`,
which preserves the original inode, owner and mode. Confirmed unchanged at
-rw-rw-r-- tomigj:tomigj. The build spec has been amended to specify `cat`.

of evidence than the alerts and a stronger one.
